# Переезд на реальный MCP: что обсудить с командой

Список нюансов, которые всплыли при сравнении нашего контракта (`docs/mcp-contract.md`) с MCP робота команды (`oc-mcp`). Файл пополняется по ходу работы, чтобы ничего не потерялось к встрече.

Коротко о схеме. Скиллы и стенд рассчитаны на высокоуровневый API в мировых координатах (`move_to`, `place_at`, `verify_blocks`, коды ошибок). `oc-mcp` даёт низкоуровневые относительные действия (`move`, `turn`, `place`, работа со слотами) и текстовые ответы. Чтобы не ждать доработок, мы пишем свой адаптер: MCP-сервер, который запускает `oc-mcp` дочерним процессом, вызывает его tools как обычный MCP-клиент, отдаёт их агенту и добавляет наши. Когда всё заработает, функциональность адаптера стоит перенести в `oc-mcp`.

## 1. Костыли адаптера

Подробности в коде адаптера. Его можно отдать автору `oc-mcp` с просьбой посмотреть, как встроить это в мост напрямую.

- Адаптер запускает `oc-mcp` (`bridge/server.py`) своим дочерним процессом и единственный говорит с ним по stdio. Мост живёт в одном экземпляре (порт 8765), поэтому второй клиент к нему подключиться не может.
- Ошибки переводятся в наши коды по шаблонам текста из Lua (`moved X of N blocks` в `BLOCKED`, `slot N is empty` в `NO_ITEM` и так далее). Переформулировка сообщения в Lua ломает перевод, код становится `UNKNOWN`.
- Ответы заворачиваются в конверт `{ok, error_code, message, data}` обычным результатом. Сам мост отдаёт ошибки как JSON-RPC error.
- `get_action_log` ведёт адаптер: он видит каждый вызов.
- `move_to`, `face`, `place_at` и `get_status` собраны из `move`, `turn`, `place`, `inventory_scan` и `world_info`.

## 2. Решения, которые стоит пересмотреть

- `move_to` ищет путь по оракул-карте: снимку мира из region-файлов сервера стенда. Это честно только для тестов, в обычной игре такой карты нет. Замена: разведка через `surroundings` и `geo_scan` или реализация поиска пути из пункта 2.
- У робота стоит Angel Upgrade, чтобы ставить блоки без опоры рядом. Без него `place_at` должен выбирать сторону с опорой, а нависающие части строить через временные опоры.
- Рецепты NEI на стенде берутся из прогретого кэша сервера (`<мир>/ocnei/cache.json.gz` в шаблоне мира). Без игрока онлайн сервер отдаёт их с `stale: true`. Запрос мимо кэша даёт `NO_PROVIDER`, и такой прогон считается невалидным. Кэш надо перегревать при смене модов или сценариев.
- Робот собирается один раз руками и живёт в шаблоне мира на парковке вне регионов сценариев. Перед каждым прогоном `real_setup` через адаптер выгружает его инвентарь в сундук-мусорку и ведёт его на старт сценария. Сброс региона и судья игнорируют блоки робота (`OpenComputers:robot` и след движения `robotAfterimage`).
- В конфиге OC сервера стенда `ignorePower=true` (робот не разряжается) и поднят `limitFlightHeight`. В обычной игре энергия и высота полёта снова станут ограничениями.
- Мост поднимают по очереди conformance, `real_setup` и агент, параллельно нельзя. Журнал действий адаптер пишет в файл, потому что процесс адаптера завершается вместе с агентом.
- Демо идёт на том же выделенном сервере стенда, к которому подключён клиент игрока с теми же модами. Одиночная игра не подходит: она встаёт на паузу без фокуса окна, и у неё нет RCON для оракул-карты. Игрок не должен стоять в зоне стройки, оракул не видит сущности.

## 3. Чего не хватает в oc-mcp

- Коды ошибок в ответах Lua, например `return false, "NO_ITEM", "slot 3 is empty"`. Сейчас только текст, адаптер угадывает код по шаблонам.
- Ошибки выполнения tool как результат с `isError: true`, как велит спецификация MCP. JSON-RPC error разные клиенты показывают модели по-разному.
- Энергия робота в ответах и код `NO_ENERGY`. Сейчас разряженный робот просто перестаёт отвечать, и это неотличимо от `CONNECTION_LOST`. Для стенда план отключить расход энергии в конфиге OC.
- Поиск пути (`move_to`). Нет информации, кто и в каком виде его отдаёт (пункт 2).
- `verify_blocks`: сверка списка блоков с миром. Робот видит точные имена только соседних блоков. На стенде проверку делает судья по снимку мира.
- Журнал действий (`get_action_log`) нужен для метрик стенда.
- Чтение состояния машин: энергия, тепло, активность. В v2 такого tool нет (`read_block_info` из v1 удалён), функциональные проверки машин идут косвенно через `storage_scan`: топливо тратится, компоненты реактора не плавятся. Вопрос к команде: может ли робот читать машины IC2 через драйверы OC.
- Полная выгрузка рецептов NEI для прогрева кэша. Она в планах OC NEI Bridge, пока прогреваем своим скриптом при подключённом клиенте.
- Проверка OC NEI Bridge в игре. В README мода сказано, что он ещё ни разу не запускался, хотя jar уже собран. Особенно важно поведение кэша без игрока онлайн.
- Id рецептов NEI действуют только до перезагрузки выдавшего их компьютера. Скиллы не должны хранить их между фазами, только id предметов.
- Память робота: мод рекомендует от 1 МБ (две планки третьего уровня).
- **TODO, блокер для модовых сценариев.** `inventory_scan` и `storage_scan` печатают имя стека без damage (`minecraft:planks`), поэтому адаптер не отличит `IC2:itemPlates:4` от `IC2:itemPlates:0` по тексту. Контракт v2 обещает `data.slots[].name` с damage. Попросить автора печатать `name:damage` при damage не 0 (как уже делает `blockName`) или отдавать слоты JSON. Пока правки нет, адаптер считает damage равным 0: ванильные сценарии работают, машины IC2 (`IC2:blockMachine:0` корпус и `:3` Macerator) и виды досок неразличимы.
- Поля `data`, которые сейчас может дать только адаптер: `pos` у `place` и `swing` (нужен метрикам стенда), `slots` у `inventory_scan` и `storage_scan`.

## 4. Сборка модов: расхождения со сборкой команды

Эталон стенда это сборка команды (`mods.zip`), манифест в `stand/server/mods.yaml`. Forge 1.7.10 пускает клиента на сервер, только если списки модов совпадают, поэтому для демо клиент должен стоять ровно на сборке стенда. Сверху сборки команды у нас есть:

| Мод | Версия | Зачем | Что попросить у команды |
|---|---|---|---|
| UniMixins | 0.3.2 (`+unimixins-all-1.7.10-0.3.2.jar`) | Загрузчик миксинов. Без него OC NEI Bridge не стартует | Добавить в общую сборку |
| OC NEI Bridge | 0.1.0-dev (`ocnei-0.1.0-dev.jar` из `build/libs`) | Компонент `nei` для tools `nei_*` в `oc-mcp` | Добавить в общую сборку. Подтвердить, что брать jar без суффикса `-dev` |
| CodeChickenLib | 1.1.3.141 | Его требует CodeChickenCore 1.0.7.48. В сборке команды его нет, CodeChickenCore скачивает его сам при первом запуске | Положить в сборку явно, автозагрузка ломается без сети (на стенде она уже оставляла битый файл) |

Проверено на стенде 2026-11-11: сервер стартует, OC NEI Bridge доходит до `ServerStarted`, блоки IC2 ставятся. Рецепты и конфиги IC2 2.2.828 совпадают с 2.2.827 байт в байт, поэтому фикстуры знаний стенда не менялись, только номер версии. Forge 10.13.4.1614, последняя для 1.7.10. Версию Forge у команды стоит сверить.

AE2 и Forestry сценариям не нужны, но стоят ради совпадения с клиентом. Они добавляют свои рецепты, и `nei_craft_tree` может выбрать не тот путь крафта, что ждут фикстуры. Для сценариев s02 и s04 это надо перепроверить.

## 5. memory-mcp

Стенд и скиллы его пока не используют. Прогоны изолированы, а память между ними ломает повторяемость. Если подключать, то с отдельной пустой базой на прогон (`MEMORY_DB` в рабочей папке агента). В скиллах он пригодится позже: `brief` в начале задачи вместо повторных поисков склада и машин.

Несостыковки с `oc-mcp`:

- `item_uid` проверяется шаблоном `^[a-z][a-z0-9_]*:[A-Za-z0-9_.\-/]+$`, а NEI и `oc-mcp` отдают id вида `mod:name:damage`. `minecraft:iron_ingot:0` не проходит из-за второго двоеточия, `IC2:blockMachine:3` ещё и из-за заглавных букв в моде. Нужно договориться об одном формате id.
- Документация memory-mcp ссылается на `nei.resolve` и `nei-mcp`, которых нет. Есть `nei_find` в `oc-mcp`.
- Там же упомянут отдельный path-сервис. Уточнить у автора пункта 2, в каком виде будет поиск пути.

## Новые коды ошибок в нашем контракте

- `UNSUPPORTED`: у робота нет нужного компонента. В `oc-mcp` это ответ `tool X is disabled: ...`.
- `NO_PROVIDER`: нет данных NEI, потому что нет игрока онлайн и ответа нет в кэше. Совпадает с кодом самого OC NEI Bridge.
